# ADR-0016: Android SDK in Claude Code cloud sessions

- **Status:** Accepted
- **Date:** 2026-09-25
- **Related:** PRD-0002 (CI-07), ADR-0013

## Context

Agents in Claude Code cloud sessions (claude.ai/code and the scheduled Routine
that works on `ready-for-agent` issues) start in a fresh container with JDK 21
and network access to `dl.google.com`, `maven.google.com`, Maven Central and
`services.gradle.org`, but no Android SDK. They could not run
`./gradlew lintDebug testDebugUnitTest` and had to push blind and wait for CI.

A second blocker showed up while fixing this: `gradle/gradle-daemon-jvm.properties`
(generated by Android Studio's `updateDaemonJvm`) required a **JetBrains** JDK 21
for the Gradle daemon. The container's JDK 21 is Ubuntu OpenJDK, and the
fallback download goes through `api.foojay.io`, which the cloud network policy
blocks. `org.gradle.java.home` does not override daemon JVM criteria.

## Decision

- We commit a Claude Code **SessionStart hook**: `.claude/settings.json`
  registers `.claude/hooks/session-start.sh`.
- The hook runs only when `CLAUDE_CODE_REMOTE=true`; on laptops it exits
  immediately.
- It installs a pinned, SHA-1-checked Android command-line tools archive into
  `$HOME/android-sdk` (or an existing `$ANDROID_HOME`), accepts the licenses and
  installs what the build needs: `platforms;android-36`, `build-tools;36.0.0`
  and `platform-tools`. With these present it does no network work and finishes
  in milliseconds.
- It exports `ANDROID_HOME`/`ANDROID_SDK_ROOT` via `$CLAUDE_ENV_FILE` and writes
  a git-ignored `local.properties` with `sdk.dir` if none exists.
- On first install it warms the Gradle cache with `./gradlew --no-daemon help`
  (best effort).
- It **fails soft**: any failure prints one `session-start: WARNING: …` line
  and exits 0 so the session still starts.
- It runs synchronously, with a 600 s timeout for a cold container, so the SDK
  is ready before the agent's first command.
- We drop `toolchainVendor=JETBRAINS` from `gradle/gradle-daemon-jvm.properties`.
  The daemon still requires JDK 21, but any vendor's JDK 21 now qualifies; the
  JetBrains Runtime bundled with Android Studio still matches, and the
  `toolchainUrl.*` entries still provision a JetBrains JDK where none is installed.

## Alternatives considered

- **Document manual setup steps** — agents run unattended; manual steps defeat
  the purpose.
- **Install the SDK in the environment's setup script** — lives outside the repo,
  so it is not reviewed or versioned with the build it serves.
- **Provide a JetBrains JDK from the hook** — its download hosts
  (`api.foojay.io`, `cache-redirector.jetbrains.com`) are blocked by the network
  policy, and nothing in the build depends on JetBrains-specific JDK features.
- **Async hook** — faster session start, but the agent could run Gradle before
  the SDK is there.

## Consequences

- Cloud sessions can run the same checks as CI before pushing.
- When `compileSdk` or AGP changes the required build-tools version, update
  `SDK_PACKAGES` in the hook, or Gradle downloads the missing package on every
  fresh container. The pinned command-line tools can be bumped independently.
- Gradle dependencies still come from Maven Central at build time; transient
  HTTP 429 rate limits from Maven Central have been seen in cloud sessions and
  are fixed by re-running.
- Instrumented tests (`connectedDebugAndroidTest`) still need an emulator and
  are not covered.
